# 2026-11-02 — 海面饱和的「凸包矛盾」是量测假象

`2026-11-01-progress-handoff.md` §3 记的那个"硬的矛盾"不存在。管线没有绕过 `SEA_PALETTE`，也没有
多出来的一级在做偷偷压暗。是量测把**色调映射之后**的线性值，直接和**色调映射之前**的调色板常数对比了。

§4 安排的"把 deep 改纯红"单变量实验因此没有执行 —— 它会得到"近场变红"，把一个假象解释成另一个假象。

---

## 1. 机制

`node_modules/three/src/renderers/shaders/ShaderChunk/tonemapping_pars_fragment.glsl.js:170-197`：

```glsl
vec3 NeutralToneMapping( vec3 color ) {
	const float StartCompression = 0.8 - 0.04;   // 0.76
	const float Desaturation = 0.15;
	color *= toneMappingExposure;
	float x = min( color.r, min( color.g, color.b ) );
	float offset = x < 0.08 ? x - 6.25 * x * x : 0.04;
	color -= offset;                             // ← 三通道同时减同一个数
	float peak = max( color.r, max( color.g, color.b ) );
	if ( peak < StartCompression ) return color;
	...                                          // 以上为肩部，乘性，不可逆
}
```

两支都在**最后一步**（`post.ts` 用 `RenderPipeline.outputColorTransform` 默认值，tone map 是
sRGB 编码前最后一个操作），所以：

- `x < 0.08`：三通道同时减 `x`，**最小通道被抹成 `6.25x²`**。这是"G 被压掉"的全部来源，
  不是着色器的错 —— 暗紫的 min 通道本来就是 G。
- `x ≥ 0.08`：三通道平减 `0.04`，亮色整体掉约 5 L*，无色偏。

两支都是逐像素线性的，低光段可精确求逆（最小通道留了 `6.25x²` 这条线索）：

```
x             = sqrt(captured_min) / 2.5
scene_linear  = captured_linear + (x - 6.25 * x * x)
```

只有 `peak ≥ 0.76` 进肩部之后才乘性压缩、不可逆。

### 3.2 读表

三条事实，都跟"海面饱和"直接相关：

1. **`deep` 源码注释说"提到 L\* 20.8"，屏上是 L\* 9.6。** `ad24f3a` 那次提亮只落到一半，
   因为提上去的亮度被 `-x` 又吃掉了。
2. **越暗的条目色度涨得越凶**：deep +16.2、cloud shadow +14.5、sky stop_1.0 +13.9。
   所以暗部看起来是"电光蓝紫"，不是调色板写的"灰紫"。这不是过饱和，是色偏。
3. **亮色条目只有 −5 L\* / −0.3 C\***，纯平减、无色偏。

→ 中性色调映射在这个项目里不是"显示变换"，它是整个渲染器里最大的一级调色，而且**专门作用在深紫/紫罗兰上**
（这些颜色的 min 通道恰好是 G）。由此：

- 冲"海面饱和"去改 `SEA_PALETTE` 的 G 是改错了变量。**暗部的 G 由 tone map 决定，不由 palette 决定**，
  而且方向是反的：给 palette 加 G 只是把偏置支的 `x` 抬高，屏上更接近灰。
- `SEA_PALETTE` 目前这一组数值是在给一个显示变换做反向补偿。补偿量只对了一半，所以海面是"抬起且发灰"。
- K1 的"越暗越灰"、K2 的暖色 C\* 缺口，可能同根，但**本文不下结论**——需要按新口径重测才知道。

## 4. 口径修正（从今以后）

凡是"量测像素 vs 调色板常数"的对比，**必须先 unfold**。`artifacts/cloud-audit/tonemap_unfold.py` 提供：

- `srgb_to_linear` / `linear_to_srgb` / `palette_linear`
- `fold` / `fold_many` / `unfold` / `unfold_many`（three r186 公式逐行对照，含肩部与降饱和）
- `hull_fit(pixel, palette)` → `(names, weights, residual)`，凸包内最近点
- `preimage(target_srgb)` → 要显示成这个颜色，`palettes.ts` 该写什么
- `palette_drift(palette)` / `frame_stats(path)` / `band_fit(path, palette, bands, title)`

判断标准改成：**展开后残差 > 1e-3 才能说"在凸包外"**。展开前的残差没有意义 —— 它一定会把
所有暗像素推到凸包边界上（本例 0.018）。

已知限制：`peak ≥ 0.76` 的像素不可逆（本帧 14.1%），高光区的像素级对比仍然不能用这把尺子；
`band_fit` 对天空要连 `SKY_PALETTE ∪ CLOUD_PALETTE` 一起拟合（天空是穹顶+云两层），实测残差
0.0008–0.003。

## 6. 顺带把海面的真实缺口量出来了：色相方向反了

拿到可逆的尺子之后，第一次可以拿 ref-01 的水面直接当"屏上目标"反解。ref-01 是已经出屏的图，
它的像素就是目标观感，`preimage()` 直接给出"要写成什么"。取样（避开机身、机翼、太阳路和暗角）：

| 区域 | ref-01 屏上 | 反解后该写 |
| --- | --- | --- |
| 左侧水面上半 | rgb(176,96,91) | rgb(183,110,106) |
| 左侧水面下半 | rgb(132,73,73) | rgb(142,92,92) |
| 右侧水面下半 | rgb(135,70,106) | rgb(145,90,119) |
| 最暗水（p10） | rgb(85,50,75) | rgb(101,76,93) |

对照我们现在的 A-cruise 近场 `rgb(41,27,90)`：

| | 近场水 | B − R | S(H) |
| --- | --- | --- | --- |
| ref-01 | rgb(132,73,73) | **−59** | 0.45 |
| 我们 | rgb(41,27,90) | **+49** | 0.70 |

两件事，都是方向性的：

1. **色相反了。** ref 的水是暖的胭脂/褐紫（R 最高、G 最低），我们的水是冷的蓝紫（B 最高、R 最低）。
   `B − R` 差了 **108**。`deep` 自己 `#322c58` 的 B/R 就是 1.76 —— 调色板先写成了蓝，tone map 再把它推得更蓝。
2. **饱和度过高。** 我们 0.70，ref 0.45。这跟 run 1 的门槛 `sea_sat_mean ≤ 0.55` 是同一个结论 ——
   那根门槛一直是对的，是"S 低 = 灰"这个解读把它带偏了。**低饱和在这里是对的，因为它同时暖。**

所以 S 系列的正确目标不是"给海面加饱和"，而是：**把水从蓝紫拉到暖胭脂，并降饱和。**

一个够用的近似（保持 0.5/0.5 的 deep+mid 混合比不变，两色同时平移到目标）：`deep` 从 `rgb(50,44,88)`
移到 **≈ rgb(102,73,77)**，`mid` 同向平移。这只是把量出来的目标换成调色板数值，**不是最终配色**。

⚠️ 口径限制：ref-01 是 16:9 91° 视场的横构图，机身在近景；我们 9:16 37° 竖构图。所以
**色相（B−R 的符号）与饱和度方向是硬的**，绝对亮度只作参考。这一条正好压在 P6（构图）那个待议项上。

## 7. 待拍板（美术方向，不是工程问题）

调色板到底应该表达什么，需要定一次，之后四份计划才不会再撞同一堵墙。四个选项：

- **A. 保持中性映射，调色板改成"屏上目标语义"**
  源码里写你要看到什么，`preimage()` 在写的时候算一遍。低风险，只动数据，今天就能对齐 ref-01 的目标色。
  代价：`palettes.ts` 的数值不再等于观感，注释必须改成"屏上目标"；每次改 tone map 都要重算。
- **B. 换成只在肩部压缩的色调映射**（0.76 以下恒等），palette 写什么就是什么。
  代价：要自建输出节点而不是用 `outputColorTransform` 默认值；`post.ts` 里"SMAA 在线性空间、
  交给 pipeline 统一变换"那条约束要重验；14.1% 高光的行为会变（该片段现在是唯一的抗溢出手段）。
- **C. palette 编译层**：源码维持屏上语义，构建时 `preimage` 成常数。
  美术改观感、不改数学，但多一层构建期魔法，调试时容易和运行期对不上。
- **D. 先只做海，不动全局**：按 §6 的表把 `SEA_PALETTE` 的 deep/mid 改到位，看一版。
  最省事，但它依赖 A 的语义（数值 = 屏上目标），事后要么补 A，要么留下一组自相矛盾的常数。

倾向 **A + D 一起走**（今天就能出一版对得上 ref-01 的海面），把 **B** 作为后续独立任务评估 ——
因为 B 会动 `post.ts` 唯一的抗溢出环节，而 K4 已经把余量算到 0.063 了。

## 8. D 已试：只改两个常数就够了，B 可以作废

用户质疑得对：也许根本不用碰色调映射，单纯改材质颜色就能到位。实测 —— 是对的，而且是精确到位。

改动只有 `SEA_PALETTE` 两行：`deep 0x322c58 → 0x5e444e`、`mid 0x4a4272 → 0x6c536b`，取值由
`preimage()` 从 ref-01 的最暗水反解而来。其余一个字节没动，tone map 仍是 `NeutralToneMapping`。

| 指标（A-cruise 近场，bottom 4%） | 改前 | 改后 | ref-01 最暗水 |
| --- | --- | --- | --- |
| 屏上中位数 | rgb(41,27,90) | **rgb(87,52,76)** | rgb(85,50,75) |
| B − R | +49 | **−11** | −10 |
| S(H) | 0.700 | **0.402** | 0.410 |

**误差 2/255。** 整列海面的剖面也核对过（horizon→底部 20 个 2.5% 条带）：`Vmean` 与 `Vstd`
逐条跟改前吻合在 ~2% 以内，也就是说这次改色**没有**压平海面的明暗结构，换掉的只是色相。

为什么能这么准：海面的暗端完全落在 tone map 的可逆区间（最小通道 0.025 < 0.08、峰值 < 0.76），
所以那里的映射是**双射**，改 palette 可以把它精确吸收掉。不可逆的只有 14.1% 的高光
（太阳路与 glint），而那属于 §6 之外的另一件事，不挡海面。

结论修正：

- **B（换 tone map）作废。** 它解决的是一个不存在的问题，还要动 `post.ts` 唯一的抗溢出环节。
- **A（屏上目标语义）降级为"注释约定"**：数值本来就等于屏上目标，只要在 `palettes.ts` 里写清楚、
  改 tone map 时拿 `preimage()` 重算一遍即可 —— 不需要额外的编译层（C 也不需要）。
- 遗留的只有一件事：暖色在等亮度下看起来比蓝更亮（Helmholtz–Kohlrausch），所以改后海面
  **观感**偏浅，尽管 `Vmean` 一致。要不要把 `deep` 再压暗一档，是美术口味，不是数学问题。
  旋钮就是把 `deep`/`mid` 的 scene-linear 一起乘一个系数，再 `fold()` 回屏上看效果。
