## Global Constraints

1. **调色单源**：颜色只改 `palettes.ts`；云体四色 `CLOUD_PALETTE`（`src/palettes.ts:97-105`）。
2. **单一太阳**：`SUN_DIRECTION`（`src/palettes.ts:17,29-33`）是云/海/天唯一太阳；云的 `DEFAULT_SUN` 由它派生（`src/clouds-compute.ts:310`）。任何"给云单独打一盏灯"的做法都违反这条。
3. **双后端 TSL**：云的节点图必须走 `three/tsl`；`onBeforeCompile` 禁用。
4. **单输出所有者**：云的 `MeshBasicNodeMaterial` 自己出 alpha（`clouds-compute.ts:486-493`），不许把雾交给后处理补。
5. **slab 单源**：`CLOUD_BAND`（`clouds-compute.ts:37`）同时被 `in-cloud.ts:10`、`puff-cloud.ts:27` 读取。改高度必须三处同看。
6. **JS 镜像不许漂**：`profileDensity`（68-80）、`cloudLighting`（121-144）、`slabRayT`（152-175）、`shaderSlabSpan`（200-221）、`posterise01`（252-257）是节点图的测试镜像，改动要两侧同时走。

## Review Focus

1. **抬覆盖度会同时改穿云体验**：`in-cloud.ts` 的白雾按高度线性上升（`IN_CLOUD.FADE_IN/OUT = 40`，`in-cloud.ts:12`），上限 `WHITEOUT_MAX = 0.6`（`in-cloud.ts:44`）。云变厚后"进云"会变成长时间糊屏。
2. **放大体量会撞 slab 顶**：`CLOUD_BAND.top = 480`，`FLIGHT.ALT_MAX = 240`（`src/game.ts:98`）。顶部 240 m 永远飞不到，只能远看——放大云的垂直结构收益只体现在远景。
3. **抬亮度会丢暗/亮分离度**：`cloud_value_mean` 现场 0.294–0.437（参考 0.419–0.563）。抬亮时盯 `cloud_tone_span`（现场 0.145–0.325，参考 0.227–0.431），别只看均值。
4. **改噪声尺度会改团数，而团数本身就不稳**：`cloud_blobs` 在三次同高度采集里读到 4/4/5，参考 3/6/8；`blob_area_frac_median` 0.0365–0.1548。**改之前先按 T0 固定采集协议**，否则改完也不知道动了什么。
5. **步数一加就掉帧**：12 步是 `CLOUD_STEPS_HIGH`（223），低档 8（224）；任何二次行进都按倍数算成本，而本仓库**没有任何 GPU 帧计时基线**（未验证）。

### 1.2 密度公式（**已测**，读码）

```
density = smoothstep(0.50, 0.68, shape) * heightMask            clouds-compute.ts:427,289-290
shape   = clamp(0.55·blobs + 0.30·coarse [+ 0.15·fine], 0, 1)   413-423, weights 见 89-93
heightMask = 0.92 · (1 − taper^1.6), taper = smoothstep(0.45,1,hFrac)   388-391,55
```

✓ 结论「密度 = smoothstep(0.5,0.68,noise) × 垂直剖面」成立。

**「缺低频天气覆盖场」成立（已测 + 推算）：** 全场景只有三个派生自同一 `noisePos` 的尺度——Worley 基频 `0.0065`（`CLOUD_NOISE_SCALE`，231）、fractal ×1.7（403）、fractal ×4.3（416）。最低频即 `1/0.0065 = 153.8 m`，正好是穹顶半径 780 m（28，509）的 1/5。**没有任何 400 m–2 km 尺度的"哪里长云、哪里留空"的场。**

**为什么这限制了团数与面积（推算）：** 153.8 m 的基频单元在 780 m 穹顶上只有 5.1 个周期 → 画面里最多只能出现约 5 个独立团块，每个团块的结构占比约 1/5。三对基线帧读到的「5 团、单团 3.65%」与该量级同阶；另一帧读到「4 团、15.5%」（§1.1b），说明朝向可以改变观感，但**改变不了"最大结构尺度只有 153.8 m"这件事**。参考是「3 团、单团 23.1%」→ 对应 400–900 m 量级的特征，需要一个低频场，而不是把 `0.0065` 调小。

### 1.4 采样与混叠（**推算**，公式为 `clouds-compute.ts:336-345`）

`dt = span / steps`，`span = min(tFar, 900) − max(tNear, 0)`，相机 y = 60 m（`FLIGHT.START_Y`，`game.ts:99`）：

| 视线仰角 | span (m) | dt = span/12 (m) |
|---|---|---|
| 3° | 231 | 19.3 |
| 5° | 499 | 41.5 |
| 7° | 613 | 51.1 |
| 10° | 698 | 58.2 |
| 15° | 765 | 63.7 |
| 20° | 798 | 66.5 |
| 30° | 770 | 64.2 |
| 45° | 544 | 45.4 |
| 60° | 445 | 37.1 |
| 90°（正上） | 385 | **32.1** |

**结论：** 用户给的「步距约 32 m」是**正上视角**那一行；巡航视线（5°–20°）实际 41–67 m。另有一个副作用：仰角 < 2.2° 时 `tBottom > 900`，`span` 夹到 0 → **地平线附近 2.2° 内一条云都没有**（推算）。

细节八度波长：`0.0065 × 4.3 = 0.028/m` → 基频 35.8 m；`mx_fractal_noise_float(...,2 octaves, lacunarity 2)` → **最细 17.9 m**（416-421）。

✓ 结论「细节八度波长约 18 m，步距约 32 m，欠采样混叠」成立，且实际更糟：巡航步距是 41–67 m，为最细波长的 2.3–3.7×；按 Nyquist 需要 dt ≤ 8.9 m（12 步对应 span ≤ 107 m）。代码侧已承认这件事——低档直接砍掉细八度并把权重归一（`cloudErosionWeights`，89-93；注释 410-411）。

### 1.5 光照（**已测**：读码）

```

body = 1 − smoothstep(0.05, 0.78, 1 − T)                     436
```

✓ 结论「light = body×(1−0.3·progress)+0.15·sun·T，无太阳方位分面」成立。`sunTight` 是**视线**与太阳的夹角，不是体积内法线朝光；因此明暗沿"进入体积的深度"走，不沿太阳方位走 → 大团必然是"中心亮、边缘暗"的同心带（现场帧可见）。

## 4. 任务

每条给：证据 → 候选方向（不写实现）→ 验收门 → 风险。

### T0 — 先固定采集协议（其它云任务的前置）

**证据（已测）：** §1.1 的口径警告——三次 cruise alt 60 采集的 `cloud_coverage` 0.338 / 0.564 / 0.633、`blob_area_frac_median` 0.0365 / 0.045 / 0.1548，差 2–4×。原因不是 shader，是朝向与时刻（12 s 飞 550 m）。

**候选方向：** 固定一套可比集合：同一朝向（例如正对太阳方位 ±5°）、同一高度、同一等待时间，每次改动前后各采 3 帧取中位。历史帧只作背景参考。

**验收门：** 同一协议下重复采集两次，`cloud_coverage` 差 ≤15%、`cloud_blobs` 相同。做不到就不要用这两行判缺陷。

**风险：** `2026-10-31-ref-gap-audit.md:56-57` 的云行结论建立在未受控帧对上，需要按新协议复核。

### T1 — 低频天气覆盖场

**证据（推算为主）：** §1.2 全场景只有一个尺度（基频 153.8 m，穹顶 780 m → 5.1 个周期），没有任何 400 m–2 km 的"哪里留空"的场；帧级"团太小太多"只在部分朝向成立（§1.1(b)）。**这条的理由是"结构上不可能出现参考那种大尺度空隙"，而不是"某一帧少了 20%"。**

**候选方向：** 引入 400–1000 m 波长的低频标量场作为**乘性覆盖门**，让 `density` 的阈值作用在 `shape × coverage` 上：`coverage` 决定"哪里留空"，`shape` 继续决定"瓣"。可选做法是二维高度无关场（避免再引一个三维八度去抢采样预算）。

**验收门（在 T0 协议下）：**
- **存在至少一个占云带 ≥ 20% 的连通块**（参考 ref-01 的中位单团 0.2308；当前最好的一帧是 0.1548）；
- `cloud_blobs` 稳定在 **2–4**（参考 3/6/8；当前 4–5）；
- `cloud_coverage` 落在 **0.45–0.58**（参考 0.541–0.663；当前 0.338–0.633，跨帧摆幅太大，要的是"稳"）；
- `cloud_value_mean ≥ 0.42`（不许因覆盖变大而掉亮，现在是 0.294–0.410）。

**风险：** 覆盖场放大 → 穿云路径变长，`whiteout01` 上限 0.6（`in-cloud.ts:44`）会变成长时间糊屏；slab 顶 480 m 与 `ALT_MAX 240` 的错配（§Review Focus 2）会让"更高的云"只出现在远景。

### T2 — 平流与分层

**证据（已测）：** §1.3 风速 1.79 m/s vs 飞机 46 m/s（29.9×），三个八度刚性随动，y 无 offset。

**候选方向：**
- (a) 给 `windOffset` 换成"高度分层"的一族速度（不同 y 平面不同位移）——这是把"贴图平移"变成"云在长"的最小改动；
- (b) 让云场随相机一起做**慢速视差**而不是纯时间推进（云是远处的天气，不该被近处的速度感绑死）；
- (c) 把整体风速提到 3–8 m/s（天气风的量级），而不是 1.5 m/s。

**验收门：** 需要**新增**指标（现在没有）——同一云团在 `?alt=60` 巡航 12 s 内的屏幕位移，以及"三个高度带的相对位移差 > 0"。目前**未验证**，先补指标再改参数。

**风险：** 云一动，`puff-cloud` 的 1000 m 回收走廊（`puff-cloud.ts:35`）与 `CLOUD_HAZE.FAR = 860`（`horizon.ts:79`）的"重绕前已完全起霾"前提要复核。

### T3 — 采样：把 900 m 的行程砍到看得见的距离

**证据（推算）：** §1.4；代码里已有"低档砍细八度"的先例（89-93）。

**候选方向：**
- (a) 把 `t1` 上限从 900（343）收到"霾饱和距离"量级（`HORIZON.HAZE_FAR = 520`，`horizon.ts:24`）→ span 减半；
- (b) 细节八度改成按屏幕导数/距离门控淡出，而不是全分辨率采样；

**验收门：** 写一条静态断言：`span(steps) / 17.9 ≥ 2`（Nyquist），以相机高度表驱动；帧上 `noise_audit.py` 的 `cloudHF` 不再低于参考（现场 0.001，参考 0.005 —— 现在现场反而更低，说明主要问题不是高频能量多，而是**每个样本都没被解析**，混叠以"低频漂移"的形式出现）。

### T4 — 光照：把"沿视线变暗"换成"沿太阳方位分面"

**证据（已测，跨帧稳健）：** §1.5 的公式；§1.1(a) 的三行稳健缺陷（`cloud_value_mean` 0.294–0.410、`cloud_tone_span` 0.145–0.294、`cloud_tone_levels` 5–7）；参考的云柱左亮右暗（`puff-cloud.ts:17-18` 已写明）。

**风险：** (a) 采样数 ×4（12→48），本仓库没有帧计时基线，必须先补 GPU timing（`未验证`）。

**状态：未动。** run 2 改的是 `pink` 的**色值**（见 §3），不是光照模型——`lit` 仍由 depth + march progress 决定，`sunTight` 仍是"视线·太阳"的 24 次幂。因此本节验收门（`cloud_value_mean ≥ 0.42`、`cloud_tone_span ≥ 0.28`、目检"一侧亮一侧暗而非同心环"）一条都没有推进；改色只是让既有光照模型的输出更接近参考的彩度。
