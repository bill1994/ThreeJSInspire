# 云层收敛设计：5 类 → 2 类（2026-11-13）

> 状态：**待批准**（brainstorming 产出，未经主人签字前不得动代码）
> 上游动机：主人手飞发现「穹顶云有硬分界 + 方块云 + 怎么那么多层云」，实跑定位见
> [`INDEX.md` §6「65° 档超域两症」](../INDEX.md)。本设计解决**分层过多**这一根因，
> 不负责 65° 绿带（那是 haze 独立项）。

## 1. 为什么改

现在的云是**三个时期分别补出来的**，没有人负责收口总数：

| 层 | 落地时间 | 解决的问题 | 模块 |
| --- | --- | --- | --- |
| 近景 puff 场 | 2026-11-02 云簇重做 | 飞行路径上的可穿云 | `puff-cloud.ts` / `puff-field.ts` / `puff-shape.ts` |
| 兜底壳层 | 2026-11-07 穿云体积感 | 相机进云后的体积感 | `puff-cloud.ts` 的 `puff-interior`（5 片） |
| 体积穹顶 | 2026-11-09 P1 → 11-11 P1.5/P2 | 头顶那片有厚度的云 | `dome-cloud{,-field,-noise,-light}.ts` |
| 地平线 deck + patch 环 | 2026-11-10 horizon | 天际线不空 | `dome-horizon.ts` |

`main.ts:558` 把这四类写成「云的四层消费端」，加上兜底壳层就是**五套东西同时在画云**。

病灶有两类，都是实跑抓到的：

1. **65° 档硬边**：`?tod=12` 帧上出现带笔直斜边与水平硬线的紫色楔形。`?dome=0` A/B 证明属穹顶家族，
   与 `dome-cloud.ts:18-19` 声称的「盒壁处 `fadeEnd` 已经让云全透明」矛盾——`fadeEnd` 按**相机距离**
   淡出，管不到视线在 slab 内的**路径长度**。来源是 `DOME_SLAB` 的出射面（云底 380 m、顶 1150 m）。
2. **贴脸平涂糊屏**：`IcosahedronGeometry(r, detail=2)`（320 面/瓣）+ `bandColorNode()` 四档硬切，
   配 `PUFF_FADE_NEAR=1.2 / FAR=10 / FLOOR=0.3`，5 m 处一瓣仍有 55% 不透明度，单片占屏数百像素。

但真正的根因不在这些数值，而是：**层数把「穿云」这件事稀释了**。头顶永远压着一层连续的云底，
路上那几朵就退化成装饰；玩家感受到的是「顶着一层天花板在飞」，而不是「天上有几块云」。

## 2. 目标（主人原话转写）

1. **上方到远方一片**：几块云浮在头顶和前头，一直退到天际线，会飘；轮廓一块一块数得出来，
   不是糊成一片；**纯背景，永远够不到、也不指望近看**。
2. **飞行路径上几块**：与飞行同层，能从中间穿过去。穿进去时白把人包围、飞机仍然看得见、云有厚度。
3. 上方那片**不是天边一条带**，是铺在这片海上、头顶也在、前方也在的一整片。

主人已明确：**不会往上飞钻到那片云的上面**；只有同层云参与穿越。

## 3. Goal / Non-goal / Anti-goal

**Goal**

- G1 云层从 5 类收敛到 **2 类**：背景层（不可达）+ 可穿层。
- G2 删除体积穹顶全链（4 个模块 + 单测 + 装配 + 杠杆 + 扇出）。
- G3 `deck` 与 `patch 环` 合并为**单一背景层**，不再是两套重复的远云。
- G4 兜底壳层从 5 片大瓣收成 3 片细片——**保留**「云里有厚度」的观感，去掉「平板糊脸」。
- G5 白纱只在云内生效（`VEIL_INNER=0.96` / `WHITEOUT_MAX=0.45` 已落地，本设计沿用）。
- G6 性能不退化：high 档 p95 不高于现状基线（p50 20.8 ms / p95 27.9 ms）。

**Non-goal（本设计明确不碰）**

- 天穹、海面、昼夜轨道 `skyTrackAt`、月盘、toon 三渲二 `applyToonLook`——一行不动。
- 65° 档地平线绿带（haze 串色，见 INDEX §6，独立立项）。
- 战斗内容。
- puff 的平涂风格本身（三渲二需要它）。

**Anti-goal（这样改就算白改）**

- 天变空：砍完只剩两三朵云，远看一片干净到假。
- 云变贴纸：穿进去没有厚度、没有白，像穿一张纸。
- 穿云变白屏：飞机轮廓被吞掉。
- 上方层被玩家够到：背景层一旦可接近，就得按可穿云标准重做，本设计作废。
- 帧率掉：背景层成了第二个 overdraw 大户。

## 4. 约束

- **技术栈不动**：three 0.186.0、WebGPU-only、TSL 节点材质；禁 `ShaderMaterial` / `onBeforeCompile`。
- **色彩单源**：背景层与可穿层都吃 `sky-track.ts` 的 `cloudBands` / `cloudHaze`，禁旁路调色。
- **本次不追求默认画面逐位不变**：删层必然改像素，这是目标本身。
  改为只对**天穹/海面**保留既有恒等门（`sky-color-js.test.ts` 三个 protected describe 必须字节级绿），
  云层变化属预期变更，需要新的基准帧。
- **杠杆纪律**：`?puff=0` 保留原语义；`?dome=0` 随 dome 删除一并处置（见 §6）。
- **采集协议**：`?qa=frozen` + CDP 抓帧；Chrome 必须带 `--disable-features=CalculateNativeWinOcclusion`。
- `artifacts/` 只放证据和仪器。

## 5. 目标架构

### A. 背景云层（不可达）

> **⚠ 落点未定，阻塞在主人拍板（见 §11）。** 下面这组数字是初稿，reviewer 已证伪其中一条：
> 650–950 m 在现有视锥里几乎整片出画。执行前必须先按 §11 的裁决替换掉高度/距离。

- **海拔（待定）**。初稿 650–950 m，理由是「高于 `FLIGHT.ALT_MAX = 240`，靠高度保证不可达」——
  **该理由不成立**：① 现有相机的画面上沿只到地平线以上 **21.6°**（fov 60、kick 后 ≈62.5，
  瞄轴朝下 9.6°），650–950 m 在 1300–1700 m 上给出 **16.3–34.2°**，除远端 1–3° 窄条外全部出画；
  远平面 2000 m 处 950 m 仍有 23.8°，**当前视锥内没有任何距离装得下它**。
  ② 「够不到」真正来自**环跟着相机走**，不是高度。
- 形态沿用 `dome-horizon.ts` 的补丁思路：方位 bin 扇区 + 柔边贴图 billboard + 四档调色 + 慢飘，
  但**不收进 `blobs`**（不驱动白纱/镜头/台词）。
- 同屏可见 8–14 块；宽高比、扇区角、淡入沿用 `patchesFor` 现有方案——
  但这条前提是「恒定距离环」成立，一旦改距离阶梯，per-patch alpha 恒定、不做衰减的设计就作废（见 §11）。

### B. 可穿云层（近景 puff）

- 保留 puff 场（配置 25 朵，实测可见 24——净空剔除 1 朵）。
- 兜底壳层 5 → 3 片，`scale` 0.45–0.7 → 0.28–0.4，base alpha 0.1–0.18 → 0.07–0.12。
- **现场瓣近景淡出也在范围内**（reviewer Q2 裁定）：`PUFF_FADE_NEAR 1.2 / FAR 10 / FLOOR 0.3`
  在 5 m 处给 0.556 不透明度，是「贴脸面片」的一半来源。它可以调，但 `PUFF_NEAR_FLOOR`
  有写死的可读上限，**必须配自己的闸门**（穿云可读性 + 不出现「云里什么都没有」），不许只压数值。
- 白纱参数不动（`VEIL_INNER=0.96` / `INTERIOR_FADE 0.88→1`）。

### 删除清单（代码）

- `src/dome-cloud.ts`、`dome-cloud-field.ts`、`dome-cloud-noise.ts`、`dome-cloud-light.ts` 及其单测。
- `main.ts`：dome 装配、`syncSun` 的 dome 扇出、`?dome=` 解析分支、启动条 `dome` 段。
- `world.ts`：`initDomeCloud` 挂载、`setDomeVisible` 及 `world.test.ts:190-200` 的级联断言。
- `dome-horizon.ts` **没有 deck**（见下方先决条件 ③）；它只有 patch 环，整体改造成 §5-A 的背景层
  （可原地改造，也可新写 `bg-cloud.ts` 后删除，builder 定）。

### 先决条件（reviewer 2026-11-13 核查，不做会炸）

1. **`sunColorFor` 必须先搬家**。它住在 `dome-cloud-light.ts`，但 `sky-track.ts:33`、`main.ts:60`、
   `sky-track.test.ts:415` 都在 import 它。删文件前把它（连同单测）挪到 `sky-track.ts` 或新建
   `sun-color.ts`；否则昼夜轨道整条链断。
2. **背景层必须先摆脱 `DOME_SLAB`**。`dome-horizon.ts:34` 现在是 `import { DOME_SLAB } from './dome-cloud-field'`，
   `PATCH_Y_MIN/MAX` 也由它派生。背景层要自持高度常量（§5-A），否则 `dome-cloud-field.ts` 一删就断。
3. **术语纠正**：mock 里说的「deck」不是 `dome-horizon.ts` 的东西，它就是 `dome-cloud.ts` 的
   slab 本体。`dome-horizon.ts` 的头注释只是拿 deck 当参照系，容易读错。审阅/执行时别去那个文件里找 deck。

## 6. 我的判断（builder 可以改，改了要写进计划）

- `?dome=0` 改名为 `?bg=0` 或保留旧名映射到背景层——**保留旧名更省事**，但要在 `qa.test.ts:95-110` 同步语义。
- 背景层**不写深度、不做 `alphaTest` 硬切**，靠柔边贴图 alpha；硬切正是「方块云」观感的来源之一。
- 背景云慢飘 1–3 m/s 方位漂移，复用 `far-field.ts` 的拖拽思路，不新造一套。
- **「删掉 dome 硬边自动消失」降级为待证**：`?dome=0` 同时关掉 patch 环，那个 A/B **没能排除 billboard 侧**。
  几何上楔形在画面顶部、patch 只在地平线附近 9.5–16°，所以**判断仍是 dome**；但计划必须带一步
  「`?tod=12` 下只关背景层」的隔离验证，并预留一个兜底修法——不能把「白送」写进验收理由。

### 6.1 reviewer 三问的裁定（2026-11-13）

- **Q2「平板糊脸」指哪个**：**两个都是，但分工不同**。兜底壳层（`puff-cloud.ts:353-376`，
  opacityNode 无距离项）给的是整片平纱；现场瓣给的是 5 m 处 55% 的面片（`puff-field.ts:293-305`
  的 `fadeForDistance(5)=0.556`）。G4 只治前者，因此**必须另加一条近景淡出调整与其专属闸门**；
  `PUFF_NEAR_FLOOR=0.3` 有文档写明的可读上限，不能靠一味压它来解决。
- **Q3 楔形归属**：见上，**保留 dome 结论 + 加隔离步骤**，不省这一步。
- **Q4 背景层是通用模块还是单用途**：**单用途**。本设计只做这一层高空云带；
  painted-valley 总案里「扩成 6.2 km 远景条带」的野心**不在本设计范围**，将来另立模块。
  因此 §7 的「原地改造 vs 新写」按「单用途、最小改造」来选。

## 7. 留给 builder 决策

- `PUFF_DEFAULT_DETAIL` 2→3 是否值得：面数 ×4（静态一次性生成），fill 不变；能直接消掉近距面片感。
- 背景层数量 / 高度 / 风速度的具体标定值。
- 背景层要不要吃 haze 混色：吃了远处会更融合，但 65° 绿带会传染到云上。
- puff 25 朵要不要下调（性能与「几块」的观感权衡）。
- `dome-horizon.ts` 原地改造 vs 新写 `bg-cloud.ts`。

## 8. 验收

1. **抓帧矩阵**：默认 6.97° / 黄昏 / 夜 / `?tod=12`（65°），每档配 `?puff=0`、`?bg=0` 对照。
2. **三条观感逐条目检**：上方背景层可数、路上云可穿、穿云三件套（白包围 + 飞机可见 + 有厚度）。
3. **反目标检查**：抬头/远看是否变空；`?tod=12` 硬边是否消失。
4. **性能**：同会话 high 档 p50/p95 对比现状基线。
5. **结构测试**：dome 模块不存在、四层消费端降为两层、`?bg=0` 级联正确。

## 9. 风险

| 风险 | 缓解 |
| --- | --- |
| 删 dome 后天空变薄、变空 | 背景层密度标定；夜档单独抓帧复核（夜档本来就靠星点+暗色，背景云要压暗） |
| 背景层成了新的 overdraw 大户 | billboard 少而远、不写深度、单材质合批 |
| 逐位不变门被打破，回归无基线 | 只对天穹/海面保留恒等门；云层立新基准帧并入库 `artifacts/` |
| 65° 硬边消失但绿带仍在，被误读为「没修好」 | INDEX 那条独立项已拆开登记，验收时分开判 |

## 11. 待主人拍板（唯一阻塞项）

**背景层落在画面的哪里。** 现有相机的画面上沿只到地平线以上 21.6°，所以「头顶上方」这个说法在
当前相机下**不可见**。三条路，选一条才能排期：

| 方案 | 具体做法 | 代价 | 结果 |
| --- | --- | --- | --- |
| (a) 压低高度 | 350–450 m，与现 patch 同高，只把数量/散布改稀 | 最便宜；`PATCH_Y_MIN/MAX` 几乎不用改 | 看起来是「远方的云」，不是「头顶的云」 |
| (b) 推远 | 3–10 km，需抬 `camera.far`（现 2000） | 不便宜：天穹壳 R≈800 m 跟相机 tow、海面与它排深度，动 far 不是「天穹海面不动」里的免费项 | 能进画面上沿，但变成远景条带 |
| (c) 动相机 | 让视角可抬头（pitch 或 `fovKick` 上探） | 影响操作手感与既有构图契约（`portrait.ts`/`camera-rig`） | 真能看见头顶的云 |

**需要主人回答**：你说的「头顶上方」，是**画面上边那一片**，还是**真的希望飞行时能抬头看见**？
前者走 (a)，后者走 (c)，(b) 是折中且最贵。
